CARD — importing and choosing a template

MOCKUP FOR APPROVAL · NOT BUILT YET

A card is two files and always has been: a template (the shape — what boxes exist, what they are called, where they sit) and data (what goes in them). Today the app ships one template and there is no way to add another; import means data only. This adds the other half.

The split is not cosmetic — it is what makes sharing work. Casting a card sends the DATA and nothing else, a few KB, and the receiver renders it with their own copy of the template. So a template is not a document you send around; it is something every pilot in the squad installs once, and after that everyone's cards look identical on everyone's knee.

1 · Where it lives

TEMPLATES is a view of CARD, picked from the bottom bar — exactly as RECEIVED and SHARE are views of INTEL. It is not a SETUP page: choosing a template is something you do while looking at the card, not something you go and configure. The bar shows only what the view you are on can actually do.

2 · Importing a template, and naming it

Pick a .layout.json, then name it — prefilled from the name inside the file, because the person who wrote the template usually named it well and retyping a good name is a chore.

CARDTMPL+TPL

Same rule the card data already follows: refuse whole, name what is wrong, change nothing. The template you were using is still the one you are using.

The one thing I would not let you edit: the ID. A template's id is what a shared card names when it crosses the wire — the receiver looks up their copy by it. Rename the id and cards from your squadmates stop resolving; you would get "this build does not have layout X" for a template you are plainly looking at. So NAME is yours to change, ID is the file's. Two pilots can call the same template different things and still fly each other's cards.

3 · Putting data in — JSON import

DATA on the CARD view picks a .card.json. The file names its own template, so choosing a template first is not required — importing data selects the right one. What the TEMPLATES view is for is the other direction: seeing what you have, and looking at a template before you have data for it.

4 · What this means underneath

Shipped templates stay in the app (resources/layouts/) and are read-only. Yours are copied into the app's own data folder on import — copied, not referenced, so a template does not vanish because you tidied your Downloads folder. Same reasoning as the blob store: if the app needs it to render, the app holds it.

A name is stored beside the id, not written back into the file. The file you imported is never edited.
